# Сборка и проверка Outpost

## Локальная сборка

Требуются Python 3, Git и Docker с BuildKit. Команды выполняются в корне репозитория:

```sh
python3 fetch-assets.py
docker build --platform linux/amd64 -t outpost-hardened:ci .
```

Для ARM64 использовать `--platform linux/arm64` на нативном хосте либо с QEMU.
Версии и SHA256 архивов закреплены в `sources.lock.json` и проверяются при сборке.
Базовые образы закреплены digest. APK-зависимости обновляются в пределах Alpine
3.22; побайтовая воспроизводимость образа не гарантируется.

## Автоматические проверки

```sh
go test ./...
go vet ./...
python3 tests/validate-deploy.py
python3 tests/check-publication.py
sudo env OUTPOST_TEST_IMAGE=outpost-hardened:ci python3 tests/integration.py
```

`check-publication.py` проверяет содержимое Git index. Перед локальным запуском
необходимо добавить предназначенные для публикации изменения через `git add`.

Контроллеру интеграционных тестов нужен root для чтения `/proc` контейнера и
удаления собственных файлов UID 65532. Сам Outpost остаётся непривилегированным.
Тесты используют временные fixtures и контейнеры `outpost-test-*`.

| Область | Покрытие |
|---|---|
| Supervisor | Проверка конфигурации, инъекций и изоляции окружения |
| Развёртывание | Параметры Compose, запрет автоматического создания bind-каталога, синтаксис Docker run |
| Публикация | Исключение state, секретов, артефактов и распознаваемых персональных путей из Git index |
| Rsync | Передача и восстановление, протоколы 30/31, Unicode, сравнение содержимого |
| Изменения данных | Обновление, удаление, заполнение тестовой ФС с сохранением прежнего файла |
| Доступ | Ошибки пароля и модуля, запрет выхода за модуль, отсутствие listener на Docker LAN IP |
| Изоляция | Отсутствие shell, non-root, CapEff=0, NoNewPrivs=1, отдельный network namespace |
| Жизненный цикл | Рестарт, штатное завершение, отсутствие приёмника до enrollment |
| NetBird | Ответ rootless daemon через Unix socket без TUN и capabilities |

Интеграционный набор содержит 21 проверку на каждой архитектуре. Команда
`receiver-local` предназначена для тестов без NetBird; rsync при этом доступен
только на loopback. Для эксплуатации используется стандартный режим `run`.

После публикации проверить анонимное скачивание обеих архитектур и запуск rsync:

```sh
python3 tests/verify-public-image.py
```

## GitHub Actions

[Workflow](../.github/workflows/build.yml) собирает amd64 и arm64 на нативных
раннерах. На каждой платформе выполняются Go-проверки, проверка конфигурации и
полный интеграционный набор. Сводный manifest публикуется после успеха обеих
архитектур. Доступность manifest проверяется без авторизации.

- `main` публикует `edge`.
- Тег `vX.Y.Z` публикует `X.Y.Z` и `latest`; prerelease не меняет `latest`.
- Каждый запуск получает теги `run-ID-attempt` и `sha-COMMIT`.
- Pull requests выполняют проверки без публикации.
- Артефакты `verification-amd64`, `verification-arm64` и `published-image`
  содержат результаты тестов и manifest. Срок хранения задан в workflow.

Текущие результаты доступны в [Actions](https://github.com/nd4y/outpost/actions).
Digest и revision конкретного образа следует сопоставлять с соответствующим
запуском CI.

## Приёмка развёртывания

Автоматические тесты проверяют rsync и изоляцию контейнера. Они не подтверждают
полный цикл Hyper Backup на физическом NAS через действующую сеть NetBird.
Перед эксплуатацией выполнить следующие проверки:

1. Зарегистрировать приёмник и проверить назначение группы `outpost`, состояние
   peer approval и соединение P2P/relay в используемой сети.
2. Проверить TCP 8873 от разрешённого исходного NAS. Убедиться, что сторонний peer
   и другой Outpost не получают доступ, а приёмник не может инициировать новые
   подключения к исходному NAS. Проверить эффективные политики на доверенной стороне.
3. Создать небольшое многоверсионное зашифрованное задание Hyper Backup.
   Изменить и удалить тестовые файлы, выполнить повторное копирование и ротацию.
4. Запустить проверку целостности и восстановить файлы из нескольких версий.
   Сравнить содержимое или хеши с исходными файлами.
5. Проверить права DSM ACL, квоту и фактическое действие лимитов памяти/PID/swap.
   Оценить скорость и потребление памяти на объёме, близком к рабочему.
6. При требовании строгой изоляции проверить запрет исходящего LAN/host-трафика
   правилами firewall и доступность необходимых сервисов NetBird.

Успешный healthcheck или rsync round-trip не заменяет проверку восстановления.
