# Подтверждения проверки копий

[English](../en/copy-observations.md)

Подписанное владельцем разрешение указывает точное доверие домена, источник-читатель, узел-сборщик, допустимые ноды с копиями, срок действия и максимальный возраст проверки. Это отдельный маршрут метаданных. Размещение данных или квитанция передачи сами по себе его не разрешают. Ноды отправляют собственные подписанные подтверждения сборщику через исходящий mutual TLS; источник читает их через своё исходящее соединение. Обратные подключения не требуются.

Каждое подтверждение связано с разрешением, поколением, идентификатором публичного ключа ноды, уровнем проверки шифротекста и исходным временем проверки. Сборщик сохраняет и передаёт исходные подписанные байты. Он не может подменить другую ноду собой или обновить возраст старой проверки. Источник проверяет разрешение владельца и подпись каждой ноды, затем считает разные разрешённые копии. Отсутствующие, просроченные или недостоверные доказательства оставляют задание в ожидании и сохраняют представление источника.

Кеш проверки сверяет содержимое и фиксирует окно проверки. Повторные запросы сохраняют это время и не являются новой полной проверкой. Нода может потерять данные после проверки, а скомпрометированная разрешённая нода может сообщить ложные сведения о своём хранилище. Поэтому подтверждение удостоверяет результат проверки, но не гарантирует вечную сохранность. Независимое восстановление и периодическая проверка по-прежнему нужны.

Протокол разработки использует `PUT /v1/DOMAIN/observations/GRANT/GENERATION/NODE` для собственного подтверждения ноды и `GET /v1/DOMAIN/observations/GRANT/GENERATION` для назначенного читателя. Query, кодированный путь, перенаправление, учётные данные и открытые имена источников не допускаются. Оба метода требуют текущей подписанной конфигурации сборщика. Отзыв отменяет активные запросы и дожидается их завершения. Ответы и сохранённые подтверждения ограничены; нехватка места не уменьшает требуемое число копий.

Проверки реализации и полная приёмка разделены в [карте завершения](../product-status.json).

`observation-grant-sign --key OWNER_KEY --input GRANT --output NEW_SIGNED_GRANT` создаёт отдельное разрешение. Его точные байты входят в список `observations` конфигурации каждого участвующего воркера. Срок разрешения должен покрывать срок этой конфигурации. Источник использует приватный `observationFile`; `worker-observation-status --bootstrap FILE` показывает последнее сохранённое поколение/состояние/ошибку по разрешению. Ошибки наблюдения не заменяют квитанции передачи. Текущий цикл обрабатывает одно поколение по каждому разрешению за проход; разрешение включает до 32 целей, конфигурация - до 64 разрешений. Запросы метаданных используют общие ограниченные слоты воркера.

Короткие тесты проверяют подмену подписи/идентичности/возраста, запрет расширения политики, передачу исходных байтов после перезапуска сборщика, сохранение доказательств после отзыва и перезапуск источника в ожидании второй ноды. Последний тест независимо восстанавливает эту копию после остановки воркеров и удаления синтетического источника. Проверка гонок охватывает связанный путь воркера и источника. Устаревшее доказательство требует нового окна проверки; повтор не является проверкой содержимого. Планирование новых полных проверок и стоимость полного масштаба остаются открытыми.

Для обновления подтверждения после истечения возраста, разрешённого grant, нужно новое приватное окно проверки. Оно связано с grant, поколением, назначением и хешем предыдущего подписанного подтверждения. Сохранённое время начала ограничивает срок окна; истёкшая незавершённая проверка начинается заново, не обновляя время старых чтений. Неверные старые подписи и время из будущего блокируют работу. Исходное подтверждение остаётся доступным для исторической проверки до устойчивой записи нового независимо проверенного результата. Обновление не исправляет повреждённые данные и не разрешает новые передачи.

Воркер теперь обновляет истёкшее подтверждение через такое ограниченное окно и до начала требует уже полный локальный каталог. Повреждение того же размера запрещает обновление, сохраняя старые подписанные байты. Новое подтверждение публикуется только после нового успешного чтения; повтор действующего подтверждения сохраняет его байты. Эти проверки не подтверждают плановое расшифрование и исправление повреждений.
