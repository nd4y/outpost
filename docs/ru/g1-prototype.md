# G1: эксперимент с автономным потоковым комплектом файла

[English](../en/g1-prototype.md)

Это первый исполняемый эксперимент M0, а не сервис резервного копирования или принятый формат хранения. Проверяется минимальный штатный restic-репозиторий с версиями содержимого одного файла и зашифрованными описаниями. Основной репозиторий содержит и другой файл; комплект получает только выбранный поток. Исходные файлы, основной репозиторий, его индекс и кеш не монтируются в контейнер восстановления.

Доверенный эксперимент читает каждую выбранную версию через `restic dump`, затем создаёт payload snapshot в комплекте через `backup --stdin-from-command`. Сбой источника потока не должен публиковать пустой или усечённый snapshot. Описания шифруются штатным restic и содержат точные ссылки на payload snapshots, длину, SHA-256 и метаданные фикстуры. Пароль восстановления хранится отдельно. Новые криптографические примитивы, разбиение на блоки и формат пакетов не вводятся.

У варианта есть цена: для каждой версии он читает весь выбранный файл из основного репозитория и дублирует зашифрованное хранение между основной копией и комплектом. Дедупликация внутри комплекта может переиспользовать неизменившиеся блоки. Эти расходы измеряются отдельно; эксперимент не доказывает соблюдение производственного лимита трафика или допустимую стоимость. Собственный индекс комплекта входит в его зависимости и не является общим индексом основного репозитория.

## Запуск синтетической проверки

Нужны Linux amd64, Go 1.27.3, Docker, Python 3, POSIX shell, curl, bzip2 и sha256sum. Используйте разрешённый изолированный контур разработки с достаточными свободными ресурсами; реальные источники и существующие пути копий не подключаются.

```sh
go test -count=1 ./...
go vet ./...
mkdir -p out
CGO_ENABLED=0 go build -trimpath -o out/outpost-lab ./cmd/outpost-lab
curl -fL -o out/restic.bz2 https://github.com/restic/restic/releases/download/v0.19.1/restic_0.19.1_linux_amd64.bz2
echo 'f415415624dcc452f2a02b8c33641791a8c6d6d3b65bbb3543fcf9a25151585c  out/restic.bz2' | sha256sum -c -
bzip2 -dk out/restic.bz2
chmod 755 out/restic
timeout 420 sh experiments/g1/run.sh "$PWD/out/g1-run" "$PWD/out/outpost-lab" "$PWD/out/restic"
```

Каталог назначения не должен существовать. Скрипт создаёт синтетические данные и одноразовые контейнеры, удаляет только свой контейнер/образ и сохраняет файлы эксперимента для проверки. Созданные пароль и репозиторий не публикуются. Ограничения: один CPU, 768 MiB памяти контейнера, отсутствие сети, read-only образ и назначенные mounts. Условие 1 GiB диска проверяется по ограниченным входным данным и фактическому занятию; это не принудительная файловая квота. Контейнеру компилятора требуется исполняемая временная файловая система для Go tests, контейнеру эксперимента - нет.

Фикстура создаёт случайный файл 32 MiB, меняет участок 32 KiB и строит две версии. Проверяется отказ источника потока, удаляется старая история основной копии, обслуживается комплект, затем выполняется независимое восстановление только с комплектом/ключом и повтор с необязательным эталоном. Эталон сравнивает результат после восстановления, а не является его зависимостью. Неверный пароль и повреждённый шифрованный пакет должны давать ошибку. Успех выдаётся в JSON как `G1: PARTIAL_FIXTURE_ONLY`; одна фаза `prepare` никогда не заявляет успешный restore.

## Публикация, перепаковка и удаление версий

Фаза `maintenance` получает только комплект для чтения, ключ восстановления и новый выходной каталог. Она копирует обычные файлы без hard links, отклоняет ссылки и вложенный в источник путь назначения, ограничивает каждую копию 128 MiB. Исходный репозиторий на месте не изменяется.

Эксперимент сохраняет payload без описания, затем прерывает источник описания после непустого префикса. Поиск должен вернуть прежние описания без изменений, обе версии должны восстановиться. Начальные пакеты payload намеренно создаются без сжатия; `prune --repack-uncompressed --max-unused 0` обязан удалить старые и создать новые физические пакеты до повторного восстановления обеих версий. Успешного prune без изменений недостаточно.

Удаление сначала убирает описание v1 и сохраняет состояние после этой штатной команды отдельным комплектом. Затем из рабочей копии удаляются snapshots содержимого без оставшихся ссылок и выполняется prune. Payload, на который ссылается другая сохраняемая версия, защищён; общие ссылки покрыты модульной проверкой. Новые контейнеры восстанавливают только v2 из промежуточного и конечного комплектов. Исходный комплект по-прежнему должен восстанавливать v1 и v2.

Это последовательная фикстура под управлением одного процесса. Сохранённое состояние моделирует прерывание между штатными командами; принудительное завершение процесса, потеря питания, параллельные читатели и писатели, восстановление журнала и отмена во время prune не проверяются. Блокировки отдельных команд restic не делают всю последовательность транзакцией. Эти условия остаются отдельной работой по приёмке.

## Доказательства и оставшиеся условия

Фиксируются версии toolchain/образа/исходников, команды, размер фикстуры, новые байты комплекта, полное чтение открытых байтов и фактическое занятие диска. Малый прирост комплекта не означает малого общего чтения. Шифрование имён сохраняется; имена и пути фикстуры намеренно синтетические.

Открыты приёмка трафика 100 GiB/8 MiB, полные пределы стоимости, устойчивость публикации и удаления к сбоям за пределами проверенных точек, параллельное обслуживание, общие метаданные источника (ACL/xattr/hardlinks), подписанные checkpoints, передача без ключей и установка на площадках. G1 не завершён до прохождения всех применимых требований; G2 и G3 принимаются отдельно. Утилита проверяет фиксированную фикстуру и не предоставляет производственную регистрацию или копирование произвольного файла.

Расчёт места должен включать источник, основной репозиторий, автономный комплект, промежуточные копии, перекрытие пакетов при перепаковке и результаты восстановления. Даже основной репозиторий и комплект для несжимаемого файла 100 GiB вместе превышают 200 GB без учёта файловой системы. Нельзя переносить успех малой фикстуры на этот масштаб, заменять данные разреженным или сжимаемым файлом либо обходить лимит копирования. Сначала нужны отдельный масштабный сценарий и измеренный бюджет места.

Штатная работа потоков описана в документации [restic backup](https://restic.readthedocs.io/en/stable/040_backup.html#reading-data-from-a-command) и [restic dump](https://restic.readthedocs.io/en/stable/050_restore.html#printing-files-to-stdout).
