# Кандидат G3: передача между нодами и публикация полного поколения

[English](../en/peer-transfer.md)

[Контракт ограниченных окон проверки](verification-windows.md) задаёт совместимое расширение HTTPS и квитанции с исходным временем для возобновляемой проверки.

Статус: ограниченный библиотечный кандидат Linux в `internal/peer`, использующий [реплику G2](generation-replicas.md). Он передаёт настоящие зашифрованные файловые комплекты по HTTPS с взаимной аутентификацией. Полная приёмка G3, распределённая загрузка во внешние хранилища, трафик больших файлов и эксплуатация остаются **NOT_VERIFIED**. Это изменение не устанавливает воркер, рабочие сертификаты или сетевые настройки.

## Доверие и маршруты

Для каждого домена/репозитория/эпохи явно задаются `Policy`, TLS-сертификат с проверяемой цепочкой CA и закреплённые идентификаторы открытых ключей нод (SHA-256 от SPKI сертификата). Политика определяет класс своей ноды, разрешённые классы и конкретные полномочия peer на push/pull со сроком действия. Доверенный статус не выдаёт ключ расшифрования. Внешнее хранилище с S3-совместимым API или WebDAV не является peer.

Клиент принимает один явный HTTPS-адрес. Он проверяет CA, имя сервера и закреплённый идентификатор; перенаправления, прокси из окружения, обнаружение и запасные маршруты не использует. Сервер требует проверенный клиентский сертификат, TLS 1.3 и разрешённую ноду/операцию в каждом запросе. Срок полномочий и конечных сертификатов проверяется также на повторно используемом соединении. Запрос ограничен доменом; неизменяемые публичные параметры доверия реплики связывают репозиторий, эпоху и автора каталога. Отправитель не может передать другой ключ автора или объявить себя доверенным.

Политики и сертификаты фиксируются при создании клиента/сервера. Выдача, горячее обновление, подписанное владельцем распространение политик, проверка действующих полномочий репликации, ограничения firewall и отзыв уже переданного шифротекста остаются отдельными задачами. Кандидат применяет настроенные связи на своих конечных точках; заставить скомпрометированного разрешённого держателя соблюдать транзитную политику он не может.

### Офлайн-проверка объявленных маршрутов

```sh
outpost config-routes --input /private/signed-config.json \
  --trust /private/owner-public.json --node NODE_ID --domain DOMAIN_ID
```

В файле доверия укажите полученный независимо открытый ключ владельца в поле JSON `publicKey` (base64). Команда проверяет подпись, адресата и срок действия, затем выводит SHA-256 и ревизию подписанного документа. Для каждого держателя в выбранном домене она показывает кратчайший объявленный путь по направлению передачи данных. Список отсортирован по непрозрачным идентификаторам. На ребре pull получатель подключается к отправителю. У доступного локального держателя нет переходов. Для недостижимого держателя выводится `reachable: false` без переходов. Начальная нода может иметь только транзитную роль.

Отчёт описывает один подписанный документ. Храните его закрытым вместе с конфигурацией. Команда не открывает сетевые соединения и не меняет применённую конфигурацию воркера.

### Сверка двух подписанных конфигураций нод

```sh
outpost config-route-compare --input /private/signed-config.json --node NODE_ID \
  --peer-config /private/signed-peer.json --peer PEER_ID \
  --trust /private/owner-public.json --domain DOMAIN_ID
```

Оба документа должны действовать, быть адресованы указанным разным нодам и иметь подпись одного доверенного владельца. Каждая нода должна быть держателем или транзитной нодой в выбранном домене своего документа. Отчёт указывает ноду, ревизию и SHA-256 каждого документа. Команда сверяет параметры доверия домена, разрешённые классы нод, множества держателей и транзитных нод, направленные рёбра, класс и адрес каждой ноды в правилах размещения. Порядок записей, ревизии и правила для внешних хранилищ на сверку не влияют.

Проверяйте `consistent` и массив `differences` в JSON. Для двух действительных документов с расхождениями команда возвращает отчёт. При недействительном, просроченном или адресованном другой ноде документе она возвращает ошибку. Храните отчёт закрытым. Перед развёртыванием сверьте конфигурации всех участвующих нод и отдельно проверьте полномочия репликации, учётные данные и сетевую доступность.

### Проверка подписанной топологии домена

```sh
outpost config-route-audit --input /private/signed-reference.json --node REFERENCE_ID \
  --peer-configs /private/route-index.json --trust /private/owner-public.json --domain DOMAIN_ID
```

Создайте закрытый индекс с абсолютным путём к каждому доступному документу. Эталонная нода передаётся отдельно, поэтому в индекс её не включайте.

```json
{
  "format": "outpost-config-route-index-1",
  "peers": [{ "node": "PEER_ID", "config": "/private/signed-peer.json" }]
}
```

Ожидаемые держатели и транзитные ноды берутся из подписанного эталона. Отсутствующие документы перечисляются в `missingPeers`. Каждый переданный документ должен действовать, иметь подпись того же владельца и быть адресован указанной ноде. Повторные или неожиданные ноды и недействительные документы вызывают ошибку. Размер индекса ограничен 256 КиБ, суммарный размер подписанных документов - 128 МиБ.

Значение `complete: true` означает, что все ожидаемые документы представлены. Для `consistent: true` должны также совпадать графы и параметры доверия домена. Массив `differences` указывает расхождения по каждой ноде. Команда проверяет переданный набор без обращения к сети. Перед развёртыванием проверьте действующие ревизии воркеров, полномочия репликации и сетевую доступность.

## Передача и публикация

`NewServer` возвращает HTTP-сервер с TLS-настройками, но не открывает порт. Вызывающая программа передаёт допущенные каталоги реплики/журнала и сертификаты, затем явно запускает TLS. `NewClient` предоставляет `Push` и `Pull`; воркеру нужны публичные параметры проверки и шифротекст, без ключей расшифрования владельца и подписи каталога. Инициализация журнала явная, только в существующем пустом каталоге. Проверка допуска тома/UUID относится к вызывающей программе, как в G2.

| Шаг                    | Push                                                                                         | Pull                                                                                  |
| ---------------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Защита источника       | Постоянное локальное закрепление поколения                                                   | Запрос постоянного закрепления на источнике                                           |
| Приём каталога         | Проверка подписи, области и полного списка зависимостей получателем                          | Загрузка и проверка подписанного полного каталога источника                           |
| Передача               | Получатель сообщает недостающие зависимости; объекты отправляются параллельно                | Локальная реплика определяет недостающие зависимости; объекты загружаются параллельно |
| Проверка               | Получатель проверяет размеры/хеши, сбрасывает данные на диск и атомарно публикует COMPLETE   | Локальная реплика проверяет все зависимости и атомарно публикует COMPLETE             |
| Доказательство         | Квитанция получателя; независимое чтение каталога и всех объектов перед COMPLETE отправителя | Локальная квитанция полной проверки после COMPLETE реплики                            |
| Освобождение источника | Снятие локального закрепления после записи журнала                                           | Снятие удалённого закрепления после записи локального журнала                         |

Подтверждение объекта выдаётся после проверки принадлежности, неизменяемости, размера/хеша и сохранения средствами файловой системы. Уже существующий повреждённый объект блокирует операцию; карантин и исправление пока не реализованы. Прерванный приём остаётся незавершённым. Публикация повторно проверяет все зависимости подписанного каталога через транзакцию G2 и сохраняет прошлое полное поколение при ошибке. GET каталога не публикует незавершённое состояние.

Push требует явного разрешения чтения вместе с записью, поскольку проверяет получателя. Квитанция `target-full-read` является утверждением получателя. `client-full-readback` означает, что отправитель загрузил и проверил все зависимости через закреплённую ноду; `local-full-read` фиксирует проверенную локальную публикацию. Квитанции содержат цель, поколение/хеш каталога, операцию, тип проверки и время наблюдения. Это сохранённые свидетельства аутентифицированного обмена, без отдельной подписи для передачи третьим сторонам. Обратное чтение подтверждает доступность байтов в момент наблюдения, но не будущее хранение на злонамеренной ноде. Свежесть, минимальное число реплик и разрешение удалить исходный снимок не выводятся из одной квитанции.

Асинхронная промежуточная нода постоянно хранит полные поколения. Источник может отправить ей данные и исчезнуть, а получатель с одними исходящими соединениями - забрать их позже. Одновременный сквозной туннель и входящий порт у получателя не нужны. Если промежуточная нода недоступна, получатель сохраняет прошлую полную копию, а операцию можно повторить. Маршруты автоматически не добавляются.

## Повтор, сохранность и пределы ресурсов

Журнал связывает постоянный ID операции с типом, доменом/репозиторием/эпохой, поколением, peer, исполнителем и ожидаемым хешем каталога. Попытки, стадия, последняя квитанция и счётчики сохраняются после открытия заново. Изменённая привязка для той же пары peer/операция вызывает конфликт. Локальная блокировка операции исключает одновременное исполнение одного задания; неизменяемая запись допускает дубли удалённой доставки. Повтор того же вызова API продолжает работу с учётом проверенных имеющихся объектов. Интегрирующий воркер предоставляет [обнаружение по полномочию владельца](autonomous-replication.md); библиотека не создаёт маршруты и не выдаёт распределённые аренды исполнителей.

Журнал записывается через сброс файла, атомарное переименование и сброс каталога под межпроцессной блокировкой. Незавершённые временные файлы не считаются состоянием. Сбой между фиксацией реплики и журнала/ответа может оставить полную цель при незавершённой операции отправителя; повтор снова её проверит. Прерванные закрепления источника сохраняются и запрещают сборку мусора. Успешная передача с ошибкой снятия закрепления возвращает `CleanupPending` и не отменяет проверенную публикацию. Освобождение брошенных закреплений и ограниченное хранение журнала требуют отдельного разрешённого механизма обслуживания до автономной эксплуатации.

- Параллелизм: 1-4 запроса объектов; попытки: 1-3 на запрос; таймаут положительный, не более 5 минут, дополнительно ограничен контекстом и сроком полномочий/сертификатов.
- При превышении параллелизма получатель отвечает 429. Тела, заголовки и чтение ответа ограничены. Ошибки TLS, отмена и повтор не допускают перехода к открытому HTTP.
- Объекты/каталоги наследуют предел G2 в 8 МиБ; журнал допускает не более 1024 заданий и 4 МиБ. При исчерпании ёмкости новая работа отклоняется. Месяцы непрерывного планирования в пределах этого фиксированного журнала не подтверждены.
- `objectBytesSubmitted` суммирует полные тела запросов объектов по попыткам, а не фактические байты сокета. `objectBytesReceived` считает проверенные данные pull. `readbackBytes` считает успешно прочитанные при аудите каталог/объекты последней попытки. Неполные ошибочные ответы, протокольные накладные расходы и запросы метаданных сюда не входят.

По умолчанию push независимо перечитывает всё поколение в обратную сторону. Явная [политика повторного использования](readback-reuse.md) владельца разрешает прежние доказательства чтения неизменяемых объектов для точного читателя, endpoint, назначения и области доверия. Новая квитанция `client-cached-readback` сохраняет самое старое подтверждающее чтение; её уровень отличается от свежего полного чтения и утверждения получателя. Неизменённый повтор тогда читает только каталог, изменённое поколение - новые объекты. Короткие проверки на 16 МиБ измеряют тела ответов endpoint и независимо восстанавливают обе версии. Полный сетевой трафик, локальные обходы, плановая свежая проверка и предел для 100 ГиБ остаются без приёмки.

## Короткие проверки и оставшаяся приёмка

В допущенной тестовой среде Linux выполняются `go test -count=1 ./...` и `go vet ./...`. `TMPDIR` и `OUTPOST_TEST_ROOT` указывают на её том данных; исполняемые временные файлы Go выносятся отдельно, если том запрещает исполнение. Тесты создают временные ключи CA/нод и настоящие loopback TLS-соединения, без рабочих адресов и секретов.

Фикстура 2 МиБ передаёт два поколения через промежуточную ноду, удаляет исходный источник, а затем независимо восстанавливает обе версии у получателя после остановки промежуточной ноды. Сверяются байты, права и жёсткие ссылки. Другие проверки охватывают потерянный ответ после записи, перезапуск и дубли, конфликт повторного ID, ложные подтверждения, усечённые/повреждённые ответы, преждевременную публикацию, неверные/слишком большие объекты, отсутствие клиентского сертификата, неверные идентификатор/автора/домен/класс/операцию, истёкшие полномочия, запрещённые перенаправления, предел повторов/отмену и ограниченный параллелизм запросов объектов. В наборе остаются настоящие SIGKILL-тесты G2; перезапуск G3 открывает сохранённое состояние после разрыва сокета и не моделирует отключение питания.

Фикстура повреждения требует реальной подмены данных и сохраняет ответы об отмене соседних запросов. Штатная отмена параллельного чтения не считается ошибкой тестового обработчика.

`TestOfflineHistoryAcrossMaintenanceAndPolicyChange` по умолчанию моделирует три ежедневных обновления. Один получатель отключён, пока промежуточная нода меняет допущенных участников, а остальные держатели выводят прежние полные поколения. Прерванный финальный HTTPS pull сохраняет прежнее полное поколение у получателя. Повтор получает последнее поколение напрямую, и обе версии восстанавливаются после остановки источника и промежуточной ноды. Финальный вариант запускается с `OUTPOST_OFFLINE_180=1` и `OUTPOST_TEST_ROOT` на допущенном HDD. Он моделирует 180 ежедневных обновлений с полномочиями на 187 дней. Стенд не меняет системное время и не измеряет 180 календарных дней работы.

[Таблица G3](../g3-trace.json) связывает проверки ограниченной реализации со всеми шестью требованиями этапа. [Кандидат внешней загрузки](external-upload.md) расширяет покрытие REQ-27 тремя независимыми процессами, сохранёнными подписанными назначениями, подхватом работы после SIGKILL, адаптерами частей и восстановлением полной внешней цели. Одни проверки нод остаются предпосылками. Реальные ограничения и ACL S3-совместимых/WebDAV-хранилищ, потеря питания, большая история, длительные разрывы, малые объёмы памяти, полный учёт трафика и тяжёлая приёмка G1-G3 остаются открытыми. [План этапов](roadmap.md) и ограничения рабочей выкладки сохраняются.

Текущий клиент между нодами использует [окна проверки](verification-windows.md), связанные с операцией. Новые ноды возвращают `target-window-read` или `local-window-read` с самым старым подтверждающим чтением; прежний протокол сохраняет квитанции полного чтения. Проверка наличия по метаданным не заменяет обязательную итоговую проверку хешей. Новая операция начинает свежее окно. Объём содержимого за запрос ограничен, а финальный обход каталога и признаков файлов ещё требует приёмки масштаба.
