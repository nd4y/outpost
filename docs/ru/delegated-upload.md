# Автономное планирование внешней загрузки

[English](../en/delegated-upload.md)

Воркер реализует делегированное планирование без запроса к планировщику для каждого поколения. Планировщик загрузки подписывает ограниченное разрешение с точным доверием поколения, внешним профилем, допустимыми воркерами/классами, началом, окончанием и длительностью слота распределения. Владелец отдельно включает это разрешение в текущую конфигурацию каждого допустимого воркера. Нужны обе проверки. Приватные ключи планировщика и расшифровки воркерам не передаются.

Для каждого локального полного поколения допустимые воркеры выводят одинаковый канонический план версии 2 из разрешения и подписанного автором каталога. Операция связана с хешем разрешения и поколением. Деление объектов детерминировано жёстким пределом профиля. Воркер описывает по одному ограниченному объекту шифротекста и сохраняет готовый план до постановки в очередь. Защитная отметка планирования удерживает поколение до появления отдельной отметки устойчивой очереди загрузки. Отзыв политики останавливает новую работу и сохраняет незавершённые отметки.

Разрешение задаёт область полномочий, а не подписывает конкретную карту частей. Вычисленная карта не считается достоверной до сверки с настоящими байтами: должны совпасть хеши частей, целых собранных объектов и замыкание подписанного каталога. Публикация и успешные квитанции по-прежнему требуют полного обратного чтения назначения. Корректные воркеры получают одинаковые байты плана и общие идентификаторы распределения/заявок; изменённая карта не создаёт корректно восстанавливаемое поколение только благодаря действующему разрешению. Конфликты неизменяемых объектов остаются явными.

Индивидуально подписанные планы версии 1 продолжают поддерживаться. Для планов версии 2 нужен обновлённый читатель; неизвестный формат отклоняется без удаления старых поколений. Форматы объектов, частей и каталогов хранилища сохраняются. Срок действия сохранённой конфигурации и разрешения допускает автономную работу без control plane; разрешение не выдаёт новые реквизиты, получателей или право удаления.

## Настройка и восстановление работы

Подпишите `outpost-upload-delegation-1` командой `upload-delegation-sign --key PLANNER_KEY --input DELEGATION --output NEW_SIGNED_DELEGATION`. Включите канонический подписанный документ в `uploads` конфигурации, подписанной владельцем. Каждый воркер должен быть допустимым держателем домена с явным разрешением загрузки в точный профиль; повторное делегирование для той же пары домен/назначение отклоняется. Реквизиты назначения остаются в приватной локальной конфигурации. Изменение полномочий распределения создаёт другой идентификатор операции.

Воркер обнаруживает локальные полные поколения и ставит задания `outpost-external-plan-2` в очередь. `worker-discovery-status` показывает обнаружение, `worker-status` - исполнение. Приватный кэш плана учитывается в общем дисковом бюджете. При повторном использовании байты проверяются; повреждённый или конфликтующий кэш блокирует работу и сохраняется для диагностики. Полномочия текущей конфигурации подготавливаются один раз для её активного экземпляра; сохранённый план не возвращает отозванный доступ. При отзыве сохраняются защитные отметки, очереди и доказательства для явного решения о восстановлении работы или обслуживании.

Короткие изолированные тесты используют три независимых исполнителя, тестовые S3-совместимое и WebDAV-хранилища, одинаковые планы частей, обнаружение следующего поколения без обновления конфигурации и независимое восстановление старой/новой версии после остановки воркеров и удаления синтетического источника. Четыре проверки с настоящим SIGKILL покрывают запись защитной отметки планирования, сохранение плана, приём очередью и снятие отметки планирования. После перезапуска поколение остаётся защищённым, загрузка завершается, собственные отметки снимаются. Подмена области полномочий и изменённая карта частей не дают успешно опубликовать поколение.

## Оставшаяся приёмка

Планирование сейчас перечитывает локальное замыкание для каждого нового плана. Публикация назначения и квитанция каждого исполнителя по-прежнему требуют полного обратного чтения. Эти затраты не подтверждают приёмку передачи дельты. Интеграция ограничена текущими пределами каталогов, объектов, заданий и планов. При окончательной приёмке измеряются чтение для планирования, стоимость частей, повторные попытки, общие лимиты канала/аккаунта и история; см. [карту завершения](../product-status.json). Реальные пределы хранилищ и длительная эксплуатация требуют отдельных доказательств допуска.
