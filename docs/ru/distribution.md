# Кандидат поставки Linux

[English](../en/distribution.md)

Поставка находится в разработке. Сборка архива или образа не подтверждает установку, изоляцию работающего процесса, выполнение на arm64 или полную приемку продукта. Эти команды не публикуют релизный образ. Рабочая установка требует отдельно разрешенного инфраструктурного профиля.

## Сборка и проверка до установки

`scripts/build-release.py` использует точную версию Go из `go.mod`, отключенный CGO, удаление путей сборки и фиксированный базовый набор инструкций архитектуры. Он собирает `outpost` и независимый читатель `outpost-kit` для Linux amd64 и arm64. Известный образ компилятора разработки - `golang@sha256:972b4110ba0f47539a975c31e52c64765e1ff19f2d74469ae4a595c6676e80a5`; версии Go и Python нужно проверять в выбранной среде. Скрипту нужны Python3.11+ и Go1.27.3. До автономного запуска подготовьте закрепленные контрольными суммами модули Go в среде сборки.

```sh
GOTOOLCHAIN=local GOFLAGS=-p=1 python3 scripts/build-release.py --output /build/outpost-dist
python3 scripts/verify-release.py --root /build/outpost-dist --manifest-sha256 SELECTED_MANIFEST_SHA256
```

Родительский каталог результата должен существовать. Каталог результата должен быть новым, абсолютным, вне исходников и без символических ссылок в родительском пути. Существующий результат не используется повторно и не перезаписывается. Прерванная или неуспешная сборка может оставить частичный каталог; он не является принятой поставкой. Хеши исходников проверяются до и после компиляции. Итоговая квитанция содержит хеш исходников, хеш манифеста, ревизию и архитектуры. Без отдельно проверенного коммита ревизия имеет вид `dev-` с хешем точных входных файлов. Переданная метка коммита сама по себе не удостоверяет содержимое исходников. Стандартный вывод содержит только JSON-квитанцию; сообщения компилятора и проверки модулей идут в stderr. Автоматизация разбирает вывод целиком, а не выбирает последнюю строку.

Храните хеш выбранного манифеста отдельно от скачанного или скопированного комплекта. Вычисление хеша неизвестного манифеста с немедленным доверием этому значению не устанавливает происхождение. Автономный проверяющий инструмент проверяет выбранный хеш, точный набор файлов, хеши содержимого, архитектуру статических ELF, содержимое архивов и нормализованные метаданные. Дополнительные файлы, символические ссылки, измененное содержимое, пропущенные элементы и неожиданные пути отклоняются без распаковки. Результат явно отделяет проверенные артефакты от приемки работающего продукта. Архивы содержат лицензии проекта, модулей и среды Go; исходные данные и приватные профили не входят в каталог сборки.

Архив каждой архитектуры содержит оба бинарника и лицензии. Время, владелец, порядок записей и заголовки сжатия нормализованы. Равенство повторных сборок и проверки поврежденных комплектов выполняются отдельно от запуска продукта. Независимому читателю нужны выбранные ключи/контрольные точки по [контракту файлового комплекта](file-kit-format.md); упаковка не добавляет зависимости от работающего сервиса или общего каталога репозитория.

## Ведомость состава ПО

Для каждого выбранного исполняемого файла и архитектуры создайте SBOM CycloneDX 1.6. Используйте [официальный архив cyclonedx-gomod 1.12.0](https://github.com/CycloneDX/cyclonedx-gomod/releases/tag/v1.12.0) для Linux-машины, на которой формируется ведомость. Скрипт сверяет закреплённый SHA-256 архива и читает проверенные бинарники без запуска и скачивания модулей. Версия Go в окружении должна уметь читать сведения о сборке выбранных файлов.

```sh
python3 scripts/build-sbom.py --root /build/outpost-dist \
  --manifest-sha256 SELECTED_MANIFEST_SHA256 \
  --generator-archive /build/cyclonedx-gomod-linux.tar.gz \
  --output /build/outpost-sbom
```

Укажите новый выходной каталог вне дистрибутива. Итоговый `sbom-manifest.json` связывает манифест дистрибутива, ревизию, SHA-256 бинарника и SHA-256 ведомости. Храните его вместе с доказательствами выбранной сборки. В ведомости указаны включённые модули Go и версия стандартной библиотеки. Подпись релиза и приёмка установки опубликованного комплекта проверяются отдельно.

## Контейнер и подготовка приватной среды

[Dockerfile](../../packaging/Dockerfile) использует проверенный каталог результата. Он начинается с пустой корневой файловой системы и копирует только два бинарника и лицензии. В нем нет оболочки, пакетного менеджера, исходников, учетных данных и автоматической инициализации. Выберите совпадающие платформу и `TARGETARCH`, передайте проверенную ревизию, соберите локальный кандидат и сохраните неизменяемый ID образа. Сборка образа arm64 без выполнения подтверждает только кросс-компиляцию.

[Кандидат Compose](../../packaging/compose.yaml) требует явно заданные ненулевые `OUTPOST_UID`/`OUTPOST_GID` (значение образа по умолчанию65532:65532), корневую файловую систему только для чтения, удаленные capabilities, no-new-privileges, ограниченную временную файловую систему без исполнения и явные лимиты CPU/памяти/PID/логов. Он не публикует порт хоста, не использует сеть хоста, TUN, privileged или произвольные каталоги хоста. Два подключаемых пути должны существовать; автоматическое создание каталогов отключено. До проверки фактического применения на выбранной среде контейнеров это только запрошенные настройки.

Подготовьте приватный каталог конфигурации и отдельный пустой корень тома данных с владельцем, соответствующим выбранным ненулевым UID/GID процесса. Используйте одну идентичность при регистрации, инициализации и работе; установка не предусматривает смену владельца существующего рабочего тома. Сначала установите фактическое монтирование хранилища. Выполните [проверку и регистрацию тома](runtime-volume.md) отдельным локальным шагом владельца с окончательным путем контейнера `/var/lib/outpost`. Подготовьте приватные сертификаты, публичный ключ владельца и bootstrap с рабочим каталогом `/var/lib/outpost/worker`. Профили и секреты расположены в `/run/outpost`; приватные файлы с доступом группы/остальных отклоняются. Подготовке нужен отдельно ограниченный доступ на запись в каталог конфигурации. Работающие сервисы Compose подключают его только для чтения.

`outpost runtime-observe` читает фактическую идентичность процесса, маски capabilities, seccomp/no-new-privileges, флаги корневого и временного монтирования, отсутствие TUN и лимиты отдельного пространства cgroup-v1/v2. `runtime-check` отклоняет неизвестные или неограниченные параметры. Упакованные циклы воркера, команд и отчетности передают `--require-isolation`: отказ происходит до чтения приватного bootstrap. Это допуск процесса, а не подтверждение отделения сети хоста, разрешенных каталогов или порядка холодного запуска. Эти условия проверяются отдельно на выбранном хосте.

Явно инициализируйте воркер, примените подписанную владельцем политику и инициализируйте журнал отчетов при включении отчетности. Отсутствие рабочего каталога при обычном запуске является ошибкой. Не удаляйте состояние, не меняйте маркер, не заменяйте привязку bootstrap и не повторяйте инициализацию ради обхода отказа. Образ не создает центр сертификации и не придумывает учетные данные хранилища.

Укажите в `OUTPOST_IMAGE` проверенный неизменяемый локальный ID или digest образа, в `OUTPOST_DATA` - зарегистрированный корень данных, в `OUTPOST_PRIVATE` - приватный каталог профилей. По умолчанию запускается автономный воркер без ключей расшифровки. Дополнительные профили `commands`, `reports` и `telemetry` запускают отдельные процессы опроса с уже существующими приватными профилями. Они используют общий принятый журнал воркера и учет квот. Ошибка отчетности не останавливает резервное копирование. Сервис управления использует тот же бинарник, но требует отдельного [профиля управления](management-service.md), приватного каталога и зарегистрированного тома; учетные данные и среда получателя не заменяют контур оператора.

## Перезапуск, обновление и открытые проверки

Контейнер получает SIGTERM напрямую и имеет ограниченное время штатной остановки. Пример ограничивает повторные неуспешные запуски; владелец должен упорядочить старт после фактического монтирования/разблокировки. Перезапуск контейнера не доказывает холодную загрузку хоста или порядок разблокировки. Недоступный, подмененный или доступный только для чтения том должен останавливать работу без создания резервного рабочего каталога. Сетевая публикация и привилегии снимков источника относятся к отдельным принятым профилям.

До обновления сохраните прежний ID образа, приватные профили и независимо восстанавливаемые данные/контрольные точки. Используйте процедуры миграции и отката конкретных форматов; возможность перезапустить старый образ не означает совместимость с новым состоянием. Замена образа не инициализирует, не удаляет и не сбрасывает каталог данных. Приватные снимки управления восстанавливают исторические доказательства, но пока не активируют восстановленный контур управления.

Проверки артефактов ограничены и используют синтетические данные. Фактическая изоляция контейнера, запуск с сохраненной политикой, штатная остановка, замена образа, выполнение arm64, холодная загрузка, поддерживаемая смена идентичности тома, ручная приемка интерфейса и итоговый масштаб остаются этапами приемки. Отдельный [процесс телеметрии](telemetry.md) имеет устойчивую очередь отправки и короткие изолированные проверки; полное покрытие измерений и доказательства рабочего выпуска остаются открытыми. Ограниченные логи контейнера не заменяют эту очередь.

## Изолированная проверка исполнения

Скомпилируйте нативную синтетическую оснастку: `CGO_ENABLED=0 go test -c -trimpath -o /build/container-fixture.test ./cmd/outpost`. Выберите отдельно проверенные текущий и предыдущий дистрибутивы, затем выполните:

```sh
python3 scripts/check-container.py --root /build/current --manifest-sha256 CURRENT_SELECTED_HASH \
  --previous-root /build/previous --previous-manifest-sha256 PREVIOUS_SELECTED_HASH \
  --fixture-binary /build/container-fixture.test --work /build/new-container-checks
```

Нужны Linux, Docker, Compose2.15+ и явно выбранный непривилегированный владелец файлов. Сценарий собирает локальные тестовые образы только на основе scratch, не использует сеть и реальные учетные данные, сохраняет новый приватный каталог проверки. Созданные ключи не попадают в публикуемый артефакт. Обычные воркеры не подключают ключи восстановления. Проверяются ограничения ядра, отказ небезопасного запуска, явная регистрация тома, работа с сохраненной политикой, разные старый/новый образы, обновление политики, завершение по SIGTERM, откат без сброса формата, отказ отсутствующего/read-only тома, неизменность зашифрованных объектов и два независимых восстановления после удаления исходного кеша. Развертывание конфигурации Compose проверяет все четыре профиля без запуска сервисов. Удаляются только созданные этим прогоном контейнеры с его меткой; общая очистка не выполняется.

Предыдущая реализация закреплена коммитом `7747e0b7fd53b4cb4f78911eeb78053e2c58dad1`. Нативный CI собирает ее текущим упаковщиком и фиксирует итоговые входы; это не заявление о выпуске старого образа. [Нативный workflow](../../.github/workflows/distribution.yml) использует отдельные машины amd64 и arm64. Доступность ARM для публичных репозиториев описана в [справке GitHub](https://docs.github.com/en/actions/reference/runners/github-hosted-runners). Проверяйте результат точного коммита: наличие workflow не доказывает исполнение.

На cgroup-v1 нужны явно отдельное пространство cgroup и доступные контроллеры памяти, совокупной памяти+swap, квоты/периода CPU и PID. Отсутствующие контроллеры, неоднозначное монтирование, пути cgroup относительно хоста и неограниченные настройки отклоняются. Наблюдение swap для v1 означает дополнительный совокупный лимит памяти+swap, а не гарантию отсутствия физического обмена страницами ядром. Проверки разбора v1 отделены от фактического допуска хоста. Кандидат не переключает версии cgroup и не меняет параметры загрузки ядра. Отдельное пространство в Compose требует [версии2.15 или новее](https://docs.docker.com/reference/compose-file/services/#cgroup). Семантика лимитов описана в [документации контроллера памяти ядра](https://docs.kernel.org/admin-guide/cgroup-v1/memory.html).

[Комплект восстановления владельца](owner-recovery-package.md) сохраняет материал расшифрования только для чтения, исходный возраст контрольной точки и выбранные автономные инструменты в приватном хранилище владельца. Экспорт, проверка по отдельно сохранённому хешу и атомарная распаковка не передают полномочия подписи. Восстановление выбранного файла и полной реплики имеют отдельные короткие процессные проверки; жизненный цикл ключей и приёмка полного масштаба остаются открытыми.

Нативный CI также запускает `restore-external` из выбранного дистрибутива с изолированными S3-совместимой и WebDAV-фикстурами, доступными только для чтения. Проверяются полное и выборочное восстановление после отключения исходных путей. [Независимое восстановление](external-upload.md#независимое-восстановление-из-внешнего-хранилища).

## Скачиваемые кандидаты CI

Успешное native-задание сохраняет кандидат с явным списком файлов на семь дней. Имя артефакта связывает коммит, нативную архитектуру, запуск Actions и попытку. Для обеих архитектур есть отдельные доказательства нативного выполнения. Пакет содержит точный дистрибутив, контрольные суммы/лицензии, CycloneDX-файлы, связанные с бинарными файлами, обе языковые версии примечаний и `candidate.json`. Данные фикстур, ключи восстановления и журналы владельца в него не входят. Кандидат не является GitHub Release или принятой промышленной выкладкой.

Независимо выберите коммит и успешное задание. Сохраните вне скачанного пакета запись `CANDIDATE_SELECTION` из лога или квитанцию job summary: репозиторий, запуск/попытку, архитектуру, SHA-256 манифеста кандидата, внутреннего архива и артефакта Actions, а также ID артефакта. Сверьте аутентифицированные метаданные Actions API и digest скачивания. Одни контрольные суммы из самого скачанного архива не подтверждают правильность выбора. CI получает точный source head и встраивает этот коммит в бинарные файлы кандидата.

На изолированном Linux-хосте запустите проверяющий из независимо доверенного checkout этих исходников:

```sh
python3 scripts/verify-candidate-release.py \
  --archive /downloads/outpost-candidate-amd64.tar.gz --output /verification/new-candidate \
  --sha256 INDEPENDENT_CANDIDATE_MANIFEST_SHA256 --repository OWNER/REPOSITORY \
  --commit SELECTED_COMMIT --run-id SELECTED_RUN --run-attempt SELECTED_ATTEMPT \
  --native-architecture amd64
```

Ограниченный распаковщик принимает только обычные файлы USTAR. Он отклоняет ссылки, выход из каталога, повторяющиеся/специальные заголовки, превышение числа файлов/байтов, неверный provenance, потерянные файлы, изменённые бинарные файлы и несоответствующий SBOM. Существующий целевой путь не заменяется. После сбоя новый приватный каталог может остаться для анализа; повторяйте в другой новый каталог. `VERIFIED_CANDIDATE_BYTES` подтверждает выбранные байты, а не установку или здоровье резервных копий. До приёмки этапа выполните установку/обновление и независимое восстановление именно этими проверенными байтами.

Браузерное задание отдельно сохраняет пять синтетических экранов и очищенный отчёт, связанный с исходниками. Сертификаты фикстуры, `ready.json`, сырые логи, локальное хранилище браузера и сырые DOM/URL-поля axe исключены. Автоматический PASS и ручная визуальная/клавиатурная приёмка различаются. См. [примечания к кандидату](release-notes.md).

[Квитанция кандидата](../ci-candidate-evidence.json) теперь фиксирует реальные артефакты коммита `f2f332121efa9cf07af9fd9861afb4f63c7744f3` с шестью успешными обязательными заданиями CI. Оба native-архива и браузерный архив скачаны и независимо проверены. Скачанный amd64-reader восстановил обе версии по 128 МиБ и атрибуты в новых контейнерах без сети из неизменяемых объектов/каталогов, без рабочего индекса и исходного source/runtime. Старый комплект владельца сохраняет исходный манифест инструментов; новый reader выбран отдельно по CI. Визуально проверены английский desktop viewport, русская страница 375px и страница с текстом 200%. Ручная клавиатурная проверка, вспомогательные технологии, физическая холодная загрузка, полный масштаб ingress и приёмка продукта остаются отдельными этапами.
