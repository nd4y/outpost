# Подготовленные экспорты приложений

[English](../en/prepared-exports.md)

Агент источника может захватывать полный экспорт, созданный отдельно настроенным нативным средством приложения. Приватный bootstrap `outpost-source-agent-prepared-1` задаёт `profile.consistency: "application"` и связывает публичный ключ производителя, метод, исходные времена и точный состав файлов. Производитель обязан завершить согласованный экспорт до подписания. Статус `producer-signed` обозначает это утверждение производителя; подпись или совпадение хешей сами по себе не доказывают согласованность приложения.

Провайдер принимает завершённые нативные представления. Подготовленный производитель создаёт экспорт приложения или снимок файловой системы вне Outpost. Общая конфигурация не может передать команду оболочки. Обычные источники best effort поддерживаются отдельно. Неподдерживаемый провайдер согласованности получает отказ.

## Приватный допуск

Сохраните структуру bootstrap, привязку тома, HTTPS-идентичность, ключ восстановления и полномочия записи из [source-agent.md](source-agent.md). Для этого провайдера нужен новый рабочий каталог; изменение существующего bootstrap best effort не является миграцией. Через `source-probe` допустите существующий приватный родительский каталог неизменяемых экспортов. Он не должен пересекаться с рабочим хранилищем.

Измените формат bootstrap на `outpost-source-agent-prepared-1`, задайте `profile.consistency` равным `application` и добавьте:

```json
{
  "prepared": {
    "trust": {
      "profile": "PROFILE_ID",
      "origin": "ORIGIN_ID",
      "method": "native-application-export-v1",
      "producer": "BASE64_ED25519_PUBLIC_KEY",
      "maxBytes": 1073741824,
      "maxFiles": 4096
    },
    "manifestFile": "/private/current-export.json"
  }
}
```

Это заполнители внутри полного приватного bootstrap. Profile/origin должны совпадать с профилем источника, а лимит байтов производителя не может превышать `profile.maxSourceBytes`. Метод - локально согласованный идентификатор, не имя исполняемого файла. Манифест ограничен 1 МиБ и 4096 обычными файлами. Пути относительны к допущенному родительскому каталогу; имена файлов остаются приватными.

Выбранный экспорт должен содержать только подписанные обычные файлы и необходимые родительские каталоги. Отсутствующие и лишние файлы, лишние пустые каталоги, символические ссылки, дополнительные жёсткие ссылки, переходы на другие монтирования, выход за корень, изменение идентичности или содержимого вызывают отказ. Все выбранные объекты должны относиться к допущенному домену источника. Для разных политик размещения нужны отдельные явно согласованные экспорты; незаметно исключать часть допущенного экспорта нельзя.

## Производитель и захват

Нативное средство приложения создаёт и устойчиво завершает новый неизменяемый каталог, например `export-42`. Оно записывает возрастающий `sequence`, исходный `snapshotUnix`, `completedUnix` и относительный `root` в приватное описание. Завершение не может предшествовать снимку или находиться в будущем. Приватный файл ключа производителя содержит поле `privateKey`; этот ключ отделён от ключей записи и восстановления источника.

```sh
outpost source-prepared-export-create --bootstrap /private/source.json \
  --key /private/producer-key.json --input /private/export-claim.json \
  --output /private/next-export.json
```

Команда измеряет точный полный состав, проверяет устойчивую идентичность файлов, подписывает `outpost-prepared-export-1` и создаёт новый приватный файл без перезаписи. Она не открывает рабочее состояние, ключ шифрования или ключ записи источника. Затем производитель атомарно публикует манифест по настроенному `manifestFile`, сохраняя выбранный экспорт неизменным. Политику хранения производителя нужно определить до включения захвата; Outpost никогда не удаляет нативные экспорты.

```sh
outpost source-init --bootstrap /private/source.json
outpost source-next --bootstrap /private/source.json
outpost source-run --bootstrap /private/source.json
outpost source-status --bootstrap /private/source.json
```

Для инициализации первый манифест уже должен существовать. `source-next` сохраняет точный подписанный манифест под его хешем до фиксации неизменяемого intent. После устойчивой записи intent повторные попытки используют только сохранённый манифест, даже если производитель опубликовал новый указатель. Потеря сохранённого манифеста останавливает продолжение; текущий указатель не используется для его восстановления. Сбой до intent может оставить ограниченные сохраняемые метаданные без допущенной операции.

Успешный захват сохраняет исходное время снимка производителя. Следующий экспорт обязан увеличить номер производителя и не может отодвинуть ни одну исходную временную отметку назад. Неизменившийся экспорт возвращает `EXPORT_NOT_ADVANCED`; планировщик ждёт настроенный интервал повтора, сохраняя последнее завершённое поколение и его возраст. Имена обычных артефактов дают устойчивую идентичность с ключом внутри привязки провайдера: новые inode экспортов не разрывают историю версий файла.

При допуске и перед запечатыванием полностью проверяются байты. Это добавляет чтения источника; малое потребление памяти не доказывает низкий объём чтения или производительность на больших файлах. Создание нативного экспорта, занимаемое им место и изменения снимков требуют отдельного учёта ёмкости и скорости. Метаданные агента используют общую квоту, проверку тома и действующих полномочий.

## Снимки Btrfs только для чтения

Для согласованности файловой системы используйте тот же prepared bootstrap с `profile.consistency` равным `filesystem`. Укажите `btrfs-readonly-snapshot-v1` в `prepared.trust.method` и UUID исходного подтома в `prepared.trust.snapshotOrigin` в виде 32 строчных шестнадцатеричных символов. Зарегистрируйте приватный родительский каталог снимков как дерево источника. Исходный подтом и каталоги снимков должны быть доступны зарегистрированному пользователю источника с приватными правами.

Доверенный производитель запускает `btrfs subvolume snapshot -r LIVE SNAPSHOT` на хосте источника. Путь `SNAPSHOT` находится внутри зарегистрированного каталога. В существующую команду создания манифеста передаются возрастающий номер, относительный путь снимка и `completedUnix`. Если `snapshotUnix` пропущен, команда берёт время создания из ядра. Явно указанное значение должно точно совпасть. Подписанный манифест хранит UUID снимка. Перед захватом и запечатыванием агент проверяет флаг Btrfs только для чтения, исходную транзакцию, UUID исходного подтома и снимка и время создания. Обычные каталоги, writable-снимки, изменённые снимки и снимки другого источника отклоняются. Агент выполняет проверки без привилегий.

Для снимков действуют указанные выше ограничения закрытого перечня файлов. Снимки Btrfs не включают вложенные подтома. Зарегистрируйте каждый нужный вложенный подтом отдельно. Создание и хранение снимков остаются у производителя. Профиль подтверждает согласованность файловой системы. Согласованность приложения проверяется отдельно.

## Восстановление и совместимость

Сохраняется порядок контрольной точки, необходимого числа копий, освобождения провайдера и подтверждения. Освобождение записывает только устойчивое завершение потребителя; файлы производителя при этом не открываются, не удаляются и не изменяются. После запечатывания продолжению квитанции и контрольной точки не нужны данные источника. Независимое восстановление файлов и поколений использует существующий зашифрованный формат и материал восстановления.

Предыдущий исполняемый файл отказывает для нового bootstrap без изменения журнала. Совместимые зашифрованные копии он по-прежнему может восстановить. Сохраняйте рабочее состояние и используйте совместимый исполняемый файл; смена строки формата или удаление журнала не являются откатом. Ротация ключа производителя, другой корень/метод и преобразование существующих профилей требуют отдельной миграции.

Короткие тесты проверяют отказы полного состава, текущие полномочия/квоту/том, расписание неизменившегося экспорта, смену указателя, историю файлов и настоящий SIGKILL после сохранения манифеста, intent и освобождения провайдера. Тест выбранного CLI создаёт два настоящих экспорта SQLite через [Online Backup API](https://www.sqlite.org/backup.html) и [интерфейс SQLite в Python](https://docs.python.org/3.11/library/sqlite3.html#sqlite3.Connection.backup), оставляя открытой конфликтующую незакоммиченную WAL-транзакцию. После потери доступности исходных путей приложения и экспортов предыдущий и текущий исполняемые файлы восстанавливают поколения; SQLite проверяет целостность и точные закоммиченные записи. Это синтетическая проверка приложения, не приёмка остальных приложений или рабочих источников. Полная приёмка провайдеров, масштаба и продукта остаётся открытой в [карте завершения](../product-status.json).
