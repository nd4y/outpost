# Допуск тома рабочего состояния

[English](../en/runtime-volume.md)

Устанавливаемый воркер должен привязать приватный рабочий каталог к явно допущенной локальной файловой системе до инициализации. Отсутствующий, заменённый, заблокированный или доступный только для чтения том не должен приводить к созданию нового состояния в нижележащем каталоге. Допуск является отдельной локальной операцией владельца; удалённая конфигурация не выбирает новый том.

Локальная привязка содержит разрешённый абсолютный корень тома, тип и идентификатор файловой системы, inode корня и хеш приватного случайного файла-маркера. Они определяют наблюдавшуюся файловую систему/каталог; идентификатор файловой системы не называется универсально доступным UUID. До записи маркера допуск сравнивает переданное наблюдение со свежей проверкой. Компоненты пути открываются без перехода по символьным ссылкам. Рабочий каталог должен быть строгим потомком без символьных ссылок и вложенных монтирований среди существующих компонентов. Рабочая файловая система должна поддерживать принятую локальную модель блокировок/fsync; первый профиль разрешает только ext4, Btrfs и XFS.

Bootstrap, каждый цикл/запрос работающего воркера и допуск записи повторно проверяют привязку. Идентичность монтирования является текущим наблюдением, а не постоянным значением между перезагрузками. Ошибка останавливает новую работу и сохраняет накопленные данные. Удаление маркера или изменение привязки не является командой очистки либо миграции. Восстановление доступной материализованной копии остаётся отдельным процессом с чтением входных данных.

Формат `outpost-bootstrap-2` требует привязку `volume`, область которой совпадает с идентичностью ноды, и ненулевую эпоху допуска. Состояние, кеш конфигурации, учёт места, копии, журналы передачи, сессии приёма, очереди выгрузки и явная миграция индекса открываются относительно сохранённого дескриптора рабочего каталога. Подмена пути не перенаправляет их запись. Контролируемый монитор отменяет активную работу при потере идентичности; допуск проверяет привязку перед записью и повторно до сообщения об успехе. Это не делает зависший системный вызов I/O отменяемым.

Локальное зачисление использует `volume-probe --store DIRECTORY --output PRIVATE_PROBE_FILE`, затем `volume-enroll --store DIRECTORY --input PRIVATE_PROBE_FILE --node NODE_ID --epoch 1 --output NEW_BINDING_FILE`. Оба файла должны оставаться приватными. Первичное зачисление требует пустой выбранный каталог. Наличие состояния без маркера запрещает зачисление. Повтор с теми же корректными областью и эпохой идемпотентен; их изменение отклоняется. Зачисление не создаёт снимок источника и не меняет монтирование, разблокировку либо сеть хоста.

Старый bootstrap без привязки отклоняется. Поддерживаемая миграция уже привязанного тома требует отдельной процедуры смены идентичности с блокировкой старой; удаление маркера или редактирование JSON такой процедурой не является. Инициализация устойчиво создаёт принадлежащие системе каталоги и синхронизирует их родителей. Неизвестная обязательная идентичность или неподдерживаемая файловая система запрещает работу. Синтетические тесты проверяют отказ и отсутствие записи в подменный каталог; холодный старт, реальный порядок разблокировки и потеря тома во время I/O требуют отдельной инфраструктурной приёмки владельца.

## Холодный перенос диска на одном хосте

Чтобы подготовить новый приёмник к переносу, при первичном зачислении укажи проверенный корень данных, закрытый каталог полномочий с режимом `0700` на системном диске и публичный ключ владельца. Идентификаторы файловых систем данных и полномочий должны различаться. Каталог полномочий и ключи ноды остаются на системном диске вне копии данных. Помести каталог полномочий в закрытый каталог конфигурации, который смонтирован в контейнерах только для чтения. Команду переноса запускает оператор с доступом к тому же каталогу от UID приёмника. Уже установленные приёмники версии 1 продолжают использовать существующий профиль.

```sh
outpost volume-enroll --store DATA_ROOT --input PRIVATE_PROBE --node NODE_ID --epoch 1 \
  --volume-authority SYSTEM_AUTHORITY --volume-worker-directory WORKER_DIRECTORY \
  --trust OWNER_PUBLIC_KEY --output NEW_BINDING
outpost worker-volume-transition-sign --input PRIVATE_REQUEST --key OWNER_KEY --output SIGNED_PERMIT
outpost worker-volume-transition --bootstrap CURRENT_BOOTSTRAP --input SIGNED_PERMIT --output NEW_BOOTSTRAP
```

Для такого зачисления используй привязку `outpost-volume-2` и добавь `volumeAuthority` в локальный bootstrap. Сохрани одинаковые абсолютные пути в окружении служебной команды и приёмника. В дистрибутиве путь монтирования данных задаётся через `OUTPOST_RUNTIME_DATA_PATH`. По умолчанию используется `/var/lib/outpost`. Перед подготовкой копии останови приёмник и дождись завершения процессов команд, отчётов и телеметрии. Они держат общую блокировку каталога полномочий. Перенос при занятой блокировке отклоняется.

Скопируй каталог приёмника по тому же относительному пути на другую смонтированную файловую систему того же владельца. Сохрани байты, режимы и владельцев файлов. Сохрани исходный том и его метку. На новом томе нужна подготовленная копия без метки тома. Проверка использует открытые дескрипторы, сравнивает содержимое обычных файлов, права и владельцев и сбрасывает копию на диск. Ссылки, вложенные точки монтирования, дубли идентификаторов, лишние и отсутствующие файлы отклоняются. Передай владельцу результат `volume-probe` для нового корня. Выполни замер и первую попытку переноса в одном пространстве монтирования. Перенос включает чтение всех сохранённых байт с обоих томов.

Закрытый запрос содержит `format: "outpost-volume-transition-1"`, уникальный ID `operation`, точные текущую привязку `current` и путь `directory` из локального bootstrap, согласованный абсолютный корень `nextRoot` и замер `probe`. Владелец подписывает запрос вне приёмника. Приёмнику достаточно разрешения и существующего публичного ключа владельца. Новый bootstrap записывается в отдельный файл в каталоге полномочий. Область ноды и её действующие ключи сохраняются. После сверки результата явно выбери новый bootstrap и запусти тот же приёмник на допущенном томе.

При записи незавершённого переноса рабочие процессы отклоняются. Система сначала фиксирует вывод старого тома из записи, затем сохраняет новую метку и только после подтверждения обеих записей допускает новую эпоху. Старые данные остаются доступны автономному читателю. После прерывания верни доступ к обоим допущенным томам и повтори то же разрешение. После успешной активации потерянный результат можно получить с тем же разрешением и другим путём выгрузки bootstrap. Если прежний том утрачен до завершения, отдельно зачисли замену. Храни каталог полномочий вместе с этим хостом. Ранее зачисленные тома версии 1, поблочные клоны и копии всего хоста или каталога ключей выходят за пределы этого профиля. Физическую идентификацию диска, холодный запуск и разблокировку проверяй отдельно для каждой площадки.

Именованная проверка использует три отдельные тестовые файловые системы и автономно восстанавливает два сохранённых поколения при недоступных исходном файле и старом пути тома. Для прогона `OUTPOST_FENCED_VOLUME_FIXTURE` указывает на изолированный корень с точками монтирования `original`, `candidate` и `authority`. Сценарий прерывает операцию сразу после fsync метки вывода старого тома из записи. Физическая приёмка площадки остаётся отдельно.
