# Доверенная проверка содержимого

[English](../en/trusted-verification.md)

`verify-replica` проверяет подлинность и расшифровывает выбранные сохраненные версии файлов из материализованной реплики. Нужны закрытый ключ восстановления владельца и открытые ключи доверия поколения; источник, индекс состояния реплики, контроллер и другие ноды не требуются. Запускайте команду в доверенной среде владельца над сохраненным представлением данных. Обычные воркеры хранят шифротекст и не получают ключ восстановления.

```sh
outpost verify-replica --key /private/recovery-owner.json \
  --trust /private/generation-trust.json --store /recovery/replica \
  --generation EXPECTED_CHECKPOINT --output /private/new-verification.json
```

Необязательный файл `--input` содержит `{"versions":["EXACT_VERSION_ID"]}`. Без него проверяются все комплекты подписанного каталога, включая независимые старые и новые версии одного файла. Повторяющиеся и неизвестные версии отклоняются до чтения содержимого. Выбор каталога относится к восстановлению; эта команда выбирает непрозрачные идентификаторы версий.

Отчет `outpost-content-verification-1` содержит непрозрачные идентификаторы файлов/версий, счетчики, область и исходное время проверки. В нем нет имен, атрибутов, хешей открытых данных, содержимого и ключей. `DECRYPTED` означает успешную проверку подписанного конверта, метаданных, каждого зашифрованного фрагмента и хеша упорядоченного открытого потока. Открытые файлы не создаются. `UNREADABLE` означает невозможность прочитать или подтвердить версию; неверный ключ, повреждение и отсутствие данных не превращаются в диагноз носителя. При отмене непроверенные версии сохраняют `NOT_VERIFIED`. Другие читаемые версии остаются видимыми в частичном отчете.

`complete` относится только к выбранным версиям; `wholeGeneration` отдельно отражает область. Расшифрование не доказывает возможность восстановить атрибуты на целевой файловой системе, совместимость всех версий в одном выходном дереве или отсутствие более нового поколения в другом месте. Новый запуск читает данные заново. При частичном результате команда возвращает ненулевой код и сохраняет отчет в указанный новый закрытый файл. Существующие отчеты не перезаписываются. Нечитаемый или неверный каталог отклоняется до формирования отчета по версиям.

API реплики `KnownDamage` связывает журнал обнаружения с точными непрозрачными версиями, ссылающимися на известные поврежденные объекты. Это история обнаружения, не свежий scrub. После исправления объекта пустой список затронутых версий не публикует поколение: полная проверка шифротекста должна завершиться отдельно. Независимое восстановление выбранной версии возможно при повреждении несвязанных версий.

Планирование доверенного восстановления проверяет подлинность метаданных и имен до оценки количества файлов, байтов и псевдонимов; шифротекст содержимого не читается. Несколько версий одного файла требуют явного выбора для восстановления. Внутренний API умеет публиковать результат через уже разрешенный дескриптор родительского каталога, сохраняя назначение при подмене внешнего пути. [Доверенный исполнитель восстановления](trusted-recovery.md) теперь связывает эти механизмы с приватными профилями, подписанными командами и отдельным допуском ресурсов.

Короткие изолированные тесты охватывают потерю источника/индекса, сохраненные версии, точный список повреждений, восстановление незатронутого файла, неверный ключ, отмену, недопустимый выбор, несовпадение файла с каталогом, типизированные записи, приватность отчета и ненулевой статус частичного результата. Доверенное исполнение команд проверяется отдельными короткими интеграционными и аварийными сценариями. Полный масштаб и установка остаются отдельными этапами приемки.
